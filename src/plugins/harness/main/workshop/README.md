# 插件工坊（Plugin Workshop）

> 「和助手对话，把插件做出来」——助手写代码，工坊负责**构建 → 自动验收 → 装进应用**，
> 用户只在设置页看结果。功能入口：**侧栏「插件」模式** 与 **设置 → 助手 → 插件工坊**。

## 它解决什么

外部插件（`userData/plugins/<id>/`）的失败模式几乎都发生在「写好了但装不上 / 装上了但界面不出来」：

- 主进程引了宿主运行时表里没有的 `@host/main/**` 键 → 整个插件主模块装载失败，
  表现是「菜单还在、所有调用都报无处理器」；
- 渲染层引了宿主 UI 表里没有的模块、或把宿主说明符留在 chunk 里 → 白屏 / 解析失败；
- 通道名没落在自己的命名空间 → 宿主在装载期直接抛错；
- `install()` 第一行就抛（读文件/读设置）→ 插件「装上了但全哑」；
- 用了 Tailwind 类名却没带 `plugin.css` → **界面变形**（2026-09-26 的真实事故）。

这些错误靠「看一眼代码」很难发现，靠「装上去试试」又要用户自己承担。工坊把这条链路自动化：
**构建期能查出来的在构建期查，查不出来的用真实装载冒烟查，仍然查不出来的让真界面跑一遍。**

## 两个入口

| 入口                                      | 面向       | 做什么                                                                                                                                             |
| ----------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **侧栏模式开关（工作 / 插件，胶囊滑块）** | 日常使用   | 工作 = 工作区 → 会话；插件 = 插件清单（名称 + 状态），点一行打开它的工坊详情；行内「⋯ / ＋」见下；右上角 ＋ 先确保存放路径已配置，再弹「新建草稿」 |
| **设置 → 助手 → 插件工坊**                | 管理与排查 | 插件存放路径 + 插件列表 + 构建/验收/安装/停用/卸载/导出/删除 + 逐项验收报告 + 文件树只读预览                                                       |

### 插件行的行内操作（与工作区行对齐）

用户口径（2026-09-27）：「插件并没有像工作里面的工作区一样的功能……重命名插件名称」。工作区行悬停出
「⋯（重命名 / 删除）」+「＋（新建会话）」，插件行现在是同一套：

| 行内动作                   | 做什么                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **⋯ → 构建 / 验收 / 安装** | 与设置页同一个 `useDraftActions`（`renderer/components/workshop/useDraftActions.ts`）：忙碌态按 id 记、失败显示主进程原话、成功自动重拉列表——两处入口的口径不会分叉                                                                                                                                                                                                                                                                                                                                                 |
| **⋯ → 重命名插件**         | 只改**展示名**：草稿 `workshop.json` 的 `title` + 清单 `plugin.json` 的 `name`（应用里「插件管理」显示的是后者）。**不动目录名与 id**——id 同时是目录名、`plugin.json.id` 与 IPC 命名空间 `plugin:<id>:*`，改它等于换一个插件。改完产物比源码旧（`staleBuild`），要在应用里生效需重新构建/安装                                                                                                                                                                                                                       |
| **⋯ → 删除插件**           | 只删 `<插件存放路径>/<id>/` 与它的产物/报告（确认框写明「已经装进应用的插件不受影响」）；「卸载」仍在设置页，两个动作不混                                                                                                                                                                                                                                                                                                                                                                                           |
| **＋**                     | 针对这个插件开一个新会话：确保有活动工作区（没有就提示先配工作区）→ 新会话（空白）+ 把光标放进输入框（`harness-focus-input` → `HarnessInput` 的 `focus('end')`）。**一个字都不往输入框里写**（用户口径 2026-09-28「我需要的是不要显示：给插件「个人记账台账」（id: personal-ledger）这个玩意」——早先版本会预填「给插件「X」（id: y）」，已删除）：要做什么由用户自己打。**刻意不切模式**（用户口径 2026-09-27「为什么我在插件里面点击新建会话，会切换到工作」）：人还在挑插件，面板就别自己跳走，开关仍停在「插件」 |

头部右上角的「新建插件草稿」与工作模式的「新建工作区」用**同一个图标**（`RiFoldersLine`，用户口径
2026-09-27「这个按键的 icon 要和工作的 icon 保持一致」）：两个模式的头部因此完全同构
（搜索 + 设置 + 新建），回归里直接比对两处按钮渲染出的 SVG path 是不是同一段。

### 插件会话的记忆是独立的

用户口径（2026-09-28）：「插件里面的记忆应该是独立的，现在是直接使用工作里面之前选中的记忆上下文，
会导致有问题」。做法见 `main/memory-scope.ts`：

- 从插件行 ＋ 开出来的会话，记忆作用域是**这份插件**：`<memoryPath>/plugin-<插件 id>/`
  （热记忆 USER.md / MEMORY.md、档案、记忆空间、子代理记忆都在里面），与工作记忆零交叉；
- 作用域落在**话题行**上（`harness_topic.memory_scope = 'plugin:<id>'`，迁移 `0009` 加列；
  空 = 跟工作区走，老数据不用回填）——重开这个会话、甚至重启应用都还认它，
  不依赖渲染层记得住；
- 主进程按话题解析（`ipc/harness.ts` 的 `resolveTurnMemoryScope`），HarnessService / 记忆整理
  子代理 / Mnemon 单例都按作用域取目录；插件 id 会消毒（`/`、`..` 一律换 `-`），
  绝不允许靠 id 跳出 `memoryPath`；
- 工作记忆仍是 `<memoryPath>/workspace-<id>/`；两条线互不影响，卸载清数据（`purge.ts`）
  会把 `plugin-*` 作用域目录一起删掉。

### 插件会话的工作目录 = 插件自己的源码目录

用户口径（2026-09-28）：「我进行对话的时候，在插件模式下新建会话，其工作区还是之前工作模式下
选中的工作区，资源管理器也一样，还是工作模式下的工作区。解决这个bug」。

做法（`main/workshop/workspace.ts`）：插件行 ＋ 时先取（必要时创建）这份插件的**插件工作区**
——一个路径为 `<插件存放路径>/<插件 id>/` 的普通工作区行——再像切换普通工作区一样切过去。
**为什么要做成真正的工作区行**：AI 工作目录（Runtime 的 workspacePath）、资源管理器根、
文件 IPC 的边界（`assertInsideWorkspace`）、文件改动审查，全都只认 `harness.workspacePath`
+ `activeWorkspaceId`；让活动工作区真的指向插件目录，这一整条链路一行都不用改，
而且话题行记着 `workspace_id`，重开这个会话、重启应用都还回到插件目录。

- **不进「工作」列表**（用户口径同一天「插件目录不进『工作』列表，只属于那份插件」）：
  清单由主进程给（`workshop-state.pluginWorkspaces`，判定 = 路径是插件存放路径的直接子目录，
  所以**草稿删掉**的插件工作区也认得出来），侧栏据此把插件行和它自己的会话对上、
  并把这些行从工作列表里滤掉；删工作区后自动切换也跳过它们；
- **插件行可以展开**：行首那个 16px 槽位里的折叠箭头（与工作区行的文件夹图标**同槽同 x**，
  标题因此两模式都落在 30px）展开就是这份插件自己的会话，渲染走与工作区行
  **同一个** `renderTopicList`；插件会话选中时开关停在「插件」（工作会话才切回「工作」）。
  箭头**常驻**、两态不位移——用户口径 2026-09-28「折叠重复显示了…直接常驻在开头，
  和工作模式要一致」：原先它夹在标题与状态文字之间，悬停时「⋯ ＋」顶掉状态文字、箭头左移 24px
  （实测 x 156 → 132），同一个控件在两态出现在两个位置。回归 `test/probe-plugin-row-caret.mjs`
  （实机量四个态 + 截图，10/10：常驻、行首、不漂移、收起后会话行消失、与工作区行同列）；
- **老会话自动归位**：取插件工作区时会把这些会话收拢过来（`reparentPluginTopics`）——
  插件工作目录上线前开的插件会话，话题上早就是 `plugin:<id>`，`workspace_id` 却还指着当时的
  工作区（用户已有的那份插件会话就是这一类），归位后下次打开就落在插件目录上；
- 生命周期：工作区**按需创建**（第一次给这份插件开会话），插件改名时同步工作区名；
  **删除草稿不动这一行和它下面的会话**——删源码不等于删对话（与卸载插件「代码移除 / 数据保留」
  同一口径），重建同名草稿后这些会话会重新出现在插件行下。

「新建草稿」弹窗（`renderer/components/workshop/NewDraftModal.tsx`）是**两处入口共用**的同一个组件：
侧栏的 ＋ 与设置页的「新建草稿」按钮都直接弹它，框里**只有两件东西**——id、展示名
（用户口径 2026-09-27「新建插件里面不要弄一个选择插件目录」）；建完侧栏留在原地刷新列表，
设置页顺手展开它的详情。**选择存放路径的动作不在弹窗里，也不再摆空态按钮**——只有两个入口
（一个功能一个入口，用户口径 2026-09-27「不要这种描述…要像没有设置任何工作区时显示的样式保持一致」）：

- 设置 → 助手 → 插件工坊 →「插件存放路径」那一行的按钮（有路径时是「更换文件夹」）；
- 侧栏右上角的 ＋：没配路径时它**先**弹文件夹选择，选好才弹「新建草稿」。

两侧的「还没配路径」空态**与「尚未配置工作区」逐字同一副样子**：一行居中的 12px 灰字
（`text-xs text-center py-8` + `colorTextTertiary`），不写说明段落、不放按钮；工坊页的
「新建草稿」此时置灰。文案统一成「尚未选择插件存放路径」（`harness.sidebar.needPluginsPath`
与 `workshopSettings.list.needRoot` 同值），设置页那一行的说明两种状态共用一句话。

模式开关跟着**内容**走（用户口径 2026-09-27「一进来，默认不能选中插件这个栏，要看当前是在工作的
选中内容还是插件的选中内容」）：它表达的是**面板此刻在看哪一类内容**——选会话 / 新建会话 → 工作；
进工坊页（`WorkshopSettings` 挂载时派发 `harness-workshop-focus`）或从侧栏点开某份插件（同一事件）→ 插件。

它**和两侧选中的会话一起落盘、下次进来恢复**（用户口径 2026-09-28「要记住工作模式和插件模式，
选中的会话，下次进来可以记住」；覆盖 2026-09-27 的「不持久化」——那条口径的前提是内容恢复不了，
现在两侧内容一起记，开关跟着恢复出来的内容走，不会出现「侧栏列着插件、内容是工作会话」）：
设置键是 `harness.activeMode` / `harness.workContent` / `harness.pluginContent`（见
`src/main/types/settings.ts` 的 `HarnessContentRef`）。三条纪律写在 `HarnessSidebar` 的
`restoreLastContent` 上：**两份清单都读完再恢复**（否则把在册内容误判成已删除）、
**恢复跑完之前不写设置**（挂载时 mode 的初始值是「工作」，抢跑就把记住的「插件」冲掉）、
**命中不了就退回默认落点**（删掉的会话 → 该工作区的空白会话；没记住过插件 → 列表第一条）。
回归 `test/probe-session-restore.mjs`（三趟重启：工作/插件两侧各选一条 → 重启回插件那条 →
切工作侧那条还在 → 删掉它再重启 → 空白会话兜底，19/19）。

### 切模式 = 同时切到那一侧「当前那一条内容」

用户口径（2026-09-28）：「切换工作模式或者插件模式下，就默认切换到当前模式下的默认选中项的内容」。
在此之前点开关只换侧栏，主区域还停在另一侧的会话上（侧栏列着工作区、内容却是一段插件会话），
开关与内容打架。做法（`HarnessSidebar`）：

- 两个模式各自记住「当前那一条内容」（`workContentRef` / `pluginContentRef`：工作区 + 话题 id，
  话题还没落库时为 null，表示那个工作区里的空白会话）+ 工作模式最后待过的用户工作区；
  这两份记忆**同时落盘**（`rememberWork` / `rememberPlugin` 是唯一的写入口），所以「切回去」
  和「重启回来」是同一套数据、同一套兜底；
  切回去时**按 id 重读话题行**（标题可能改过），会话已被删就退回该工作区的空白会话；
- 切到「工作」：回到上次那条工作会话；没有就回到最后待过的用户工作区（一个都没有 → 回到
  「尚未配置工作区」的空白态，不把插件目录当工作区用）；
- 切到「插件」：回到上次那条插件会话；这份插件还没开过会话就走「＋」那套（取插件工作区 +
  空白会话 + 记忆作用域）——那就是插件模式里的默认选中项（还没用过任何插件时取列表第一条）；
- 内容已经在那一侧就不动（`inPluginContent` 判断）：不重复切工作区、也不莫名其妙重开会话；
- 切模式自动进入的空白会话**只带作用域、不抢光标**（`harness-focus-input` 的 `focus: false`）：
  用户只是想看那一侧的内容，不该被夺走焦点（点 ＋ 才会聚焦）。

会话行带 `data-topic-selected` 稳定钩子，工装据此断言「切过去之后选中的确实换成了上一次那条」。

### 记忆跟着**当前会话**走（两个模式都常驻）

用户口径（2026-09-28）：「插件的记忆，并没有像工作里面的记忆一样显示在侧边栏」。侧栏底部的
「记忆」块因此不再按模式隐藏，也不再固定读工作区——它读的是**当前这条会话的**记忆：

- 插件会话（话题行上 `memory_scope = 'plugin:<id>'`）→ 这份插件自己的记忆；
  插件行 ＋ 之后、话题还没落库的那一小段时间，按挂起的插件 id 走（`harness-focus-input`）；
- 工作会话 / 空白会话 → 当前工作区那套；
- 标题**只写「记忆」**，不缀作用域名（同一天用户口径「不需要（记忆 · 个人记账台账）这个内容」：
  这块本来就在会话侧，读哪一套由当前会话决定）。**设置 → 记忆页**相反，它会标出
  管的是哪份插件（`插件「番茄钟」`）——那一页脱离了会话上下文，不标就等于不知道在改谁的记忆。

作用域在渲染层放在**模块级 store**（`renderer/memory-scope.ts`，订阅式）：侧栏记忆块和
设置 → 记忆页必须显示同一份，而设置页由宿主设置弹窗渲染、**不在插件 Provider 之下**（拿不到
props），只能靠这个单例对齐。两个读取方都按它调记忆通道；记忆通道（`ipc/mnemon.ts`）末尾收一个
作用域参数，不传 = 当前工作区（老调用方行为不变），插件 id 仍然在主进程消毒。
「分支会话」会把当前作用域带进新话题——从插件会话分出来的支不该掉回工作记忆。
切会话的作用域以**话题行**为准（重开应用后点开会话也认，不靠渲染层记得住）。

## 插件存放路径（用户配置，**没有默认值**）

用户口径（2026-09-27）：「不要有默认目录，需要配置所有插件的存放路径」「不要在设置页面显示这个目录」。

- 设置里新增 `HarnessSettings.pluginsPath`；**未配置时**工坊列不出插件、也不能新建
  （空态一行灰字，配置入口见上面两个），助手侧 `plugin_draft create` 直接返回可读拒绝；
- 每个插件占一个子目录：**`<插件存放路径>/<插件 id>/`**，根目录本身**永远不会被删**
  （删除插件只删它自己那个子目录，里面的别的文件一概不动）；
- 换路径不会替用户搬旧插件（源码在旧路径里原地不动，工坊只列当前路径下的）；
- **首次配置时会把旧版目录搬过来**：早期版本把源码放在 `<userData>/plugin-workshop/drafts/<id>`，
  配置路径那一刻自动迁移（同名子目录已存在则跳过，绝不覆盖）；
- 工坊自己的东西（构建产物 / 验收报告 / 导出 zip / 那个旧目录）仍在
  `<userData>/plugin-workshop/`，**刻意不出现在设置页上**。

## 目录约定

```
<插件存放路径>/<插件 id>/        插件源码（用户选定的文件夹；能进 git、能用编辑器打开）
  plugin.json / WORKSHOP.md / main/** / renderer/** / plugin.css / workshop.smoke.mjs

<userData>/plugin-workshop/      工坊内部（界面上不展示）
  dist/<id>/                     构建产物（= 可安装插件包，与插件仓库 dist/<id> 同构）
  reports/<id>.json              最近一次验收报告
  exports/<id>-<v>.zip           导出的可分发压缩包
  drafts/<id>/                   旧版源码目录（只在首次配置时用于迁移）
```

草稿里的文件：

| 文件                            | 作用                                                         |
| ------------------------------- | ------------------------------------------------------------ |
| `plugin.json`                   | 清单（entry 由构建写入，助手不手写）                         |
| `WORKSHOP.md`                   | 契约单（生成时注入**运行期**的宿主模块白名单）               |
| `main/index.ts`                 | 主进程入口（可缺省，产物仍会有一个空 main.cjs）              |
| `renderer/plugin.tsx`           | 渲染层入口（必需）                                           |
| `renderer/*.tsx`                | 页面/组件（被 `load()` 引用的会拆成懒加载 chunk）            |
| `plugin.css`                    | 可选：手写样式（`workshop.json` 的 `css='file'` 时原样进包） |
| `workshop.smoke.mjs`            | 可选：通道级冒烟用例                                         |
| `plugin.json` / `workshop.json` | 清单与工坊元数据（模板/时间戳/css 模式）                     |

## 工作流（助手侧）

```
plugin_draft    create/list/tree/read/write/remove（插件与文件）
plugin_build    构建 + 静态体检（宿主说明符、第三方依赖、语法、chunk 绝对化、样式覆盖）
plugin_verify   构建 + 十一项验收电池（含真实装载冒烟与渲染层探针）
plugin_publish  install / disable / uninstall / export（装进应用并启用）
```

四个工具刻意按**工作流的四步**切开，而不是把十几个动作塞进一个工具：每一步的失败都要给出
「那一步专属」的可执行诊断（构建失败给 esbuild 的 `文件:行:列`，验收失败给逐项 PASS/FAIL 与建议）。

前提：工具要挂到助手身上（`mainAgent.tools`，在 **设置 → 智能体 → 工具** 里勾选）。
工坊**不提供**「一键启用」这类旁路入口——应用里所有工具都走同一条路径（2026-09-27 用户明确
不需要设置页里那块内容）。

### `layout.scan`：为什么单独查这几类（`layout.ts`）

「编译能过、界面却是坏的」这一类问题，宿主契约表与类型检查都抓不到，但它们**都能在源码层判定**，
而且每一条都对应一次真实事故（用户反馈 + 真机取证，判据与改法原样写在 `layout.ts` 的注释里）：

| 命中                                    | 症状                                                 | 正确写法                                                 |
| --------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| 撑满高度的容器带 `overflow-auto`        | 「整页滚动条」，标题/页签被滚出窗口                  | 根节点 `overflow-hidden`，要滚只滚内部内容块             |
| Tabs 的 `styles.content` 写了 `display` | 访问过的页签全部叠在一起同时画（「内容都挤在一堆」） | `content` 只给 `position/inset/minHeight/overflow`       |
| Tabs 的 `styles.content` 写了 `flex: 1` | 页签瓜分高度，当前页只剩 1/N                         | `position:absolute; inset:0` 铺满 body                   |
| `className` 里出现 `dark:`              | 暗色主题仍画浅色（`dark:` 跟的是**系统**配色）       | antd token + 宿主 `useTheme().effectiveTheme` 两份语义色 |
| `<Modal>` 没有高度上限                  | 矮窗口下滚动容器变成 `.ant-modal-wrap`，按钮滚出视口 | `formModalProps` / `createModalProps`                    |

两个刻意设计：**只扫渲染层源码且先去掉注释**（模板与真插件都习惯在注释里贴反例，
不去注释会把「教人别这么写」的文档本身判成违规）；**判据只收「确定是坑」而不收「看着可疑」**
（拿不准的一律不报，否则整条检查会因为误报失去可信度——`body: { display: 'flex' }` 是撑满高度
**必须**写的，按花括号配对逐块判定，不会被算进 `content`）。

致命项全过 = **装上去能用**；非致命项失败 = 能跑但不对。

### 渲染层探针为什么值得单独一条链路

主进程冒烟只能证明「主模块能装载」。外部插件最真实的失败是**渲染模块在宿主环境里 import 就炸**
（宿主 UI 表没有那个键、桥的具名导出对不上、注册的组件一渲染就抛）。探针在真 React / 真 antd /
真 `__RB_HOST_UI__` 表里跑一遍，并且：

- 上下文是**记录版**（注册进数组，不改动用户界面）；
- `install` 之后把所有 effect 逆序回滚，顺手验证「插件可停用」；
- 把插件声明的 `labelKey` 拿真 i18n `exists()` 逐个核对——**词条命名空间写错**（把语言当命名空间）
  是外部插件最常见也最难自查的一类错，界面上的表现只是「菜单显示 `x.menu.title`」。

## 发布与回滚

- 发布走**宿主既有的安装链路**（`installPackageDir` → `setEnabledOverride` → `loadExternalMain`
  → `broadcastPluginStateChanged`），与设置页里的「从本地安装」「从插件仓库安装」是同一批函数；
  工坊不另造一条，否则升级清理、卸载记账、渲染层重载迟早分叉。
- **装完立刻复验**：安装后自动跑一次渲染层探针；失败就**自动卸载回滚**并报原因——
  用户机器上不会留下「点了就白屏」的插件。
- `plugin_publish install` 在**没有一次通过的验收**（或产物比源码旧）时直接拒绝：
  「没验过的插件大概率是坏的」比「装完再解释」便宜得多。
- 卸载分两件事（与全应用口径一致）：**卸载插件代码**（`plugin_publish uninstall`）与
  **删除草稿**（`plugin_draft remove`）互不影响；数据是否一起删由宿主卸载确认框的勾选项决定，
  工坊模板都会带一份 `PLUGIN_PURGE` 贡献，把「删什么」写清楚。

## 实现要点（踩过的坑，改之前先读）

1. **宿主依赖是注入的**：`main/workshop/host.ts` 定义 `WorkshopHost`，`main/workshop/wiring.ts`
   是**唯一** import electron / core 的地方，其余模块只依赖 node 内置模块 —— 因此离线工装
   （`test/verify-plugin-workshop.mjs`）能用临时目录 + 假宿主把整条链路跑真。
2. **渲染层的宿主说明符必须在构建期改写成 `plugin://host/ui.js?m=<键>`**：
   懒加载 chunk 是浏览器按 `plugin://<id>/chunk-x.mjs` 自己取回来的，那条路径**没有**任何运行期
   改写机会（宿主 `external-loader.ts` 只改入口）。2026-09-27 真机实测：chunk 里残留 `from "react"`
   → `Failed to resolve module specifier "react"`。
3. **宿主运行时表的这三类键要懒加载**（`runtime.ts` 的 `lazyHostModule`）：
   `plugins/host.ts` import 了 `runtime.ts`（`installHostRuntime`），而工坊要的
   `plugins/{host,lifecycle,package-install,scanner,store}` 与 `ipc/plugins` 又（直接或间接）
   import 回 `host.ts` —— 静态 import 会成环，先求值的一侧拿到「函数还没挂上」的半成品命名空间，
   表现是 `isBundledPluginId is not a function`。懒加载代理的描述符必须报 `configurable: true`，
   否则 esbuild 的 `__toESM` 会撞 Proxy 不变量。
4. **发布必须广播 `plugin-state-changed`**（`wiring.notify`）：渲染层靠它重新拉清单、
   去 `plugin://` 取新插件的 `renderer.mjs` 并注册菜单/路由。少了这一句，插件装上了、
   通道也能用，但侧栏永远不出现 —— 极易误判成「没装上」。
5. **词条 API 是 `addResources(命名空间, { 语言: 词条树 })`**（见 `plugin-host/host.ts`）：
   写成 `addResources('zh-CN', …)` 是把语言当命名空间，界面显示原始键名。模板与 WORKSHOP.md
   都按正确形态生成，探针也会点名。
6. **样式生成用 Tailwind 的 JS API**（`css.ts`）：候选由我们自己给（`compile().build(candidates)`），
   完全不触发 Tailwind 的文件扫描 —— 打包后的应用里 `@tailwindcss/oxide`（原生模块）未必可用。
   Tailwind 装不上时降级为「不带样式」，由 `style.coverage` 如实点名。
7. **构建需要 esbuild**：从应用根 / `app.asar.unpacked` 逐个基准解析（`createNodeLoader`）。
   打包后的应用若要支持工坊构建，需把 esbuild 放进 `dependencies` 并加进 `asarUnpack`
   （拿不到时给的是可读错误，不是崩溃）。
